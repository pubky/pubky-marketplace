# Visual Regression Testing (VRT)

VRT renders a component in a real browser (Playwright via `@vitest/browser`),
screenshots it, and pixel-compares against a committed baseline. It catches
layout, styling and responsive regressions — not functional bugs (use unit /
interaction tests for those).

- Test files: `*.vrt.test.tsx`. Feed/onboarding/messages use the `vrt` Vitest
  project; marketplace files use `vrt-marketplace` (same `vitest.config.ts`).
- Compare: `npm run test:vrt` (Docker; both projects, Chromium and Firefox).
- Baselines: `__screenshots__/<file>/<name>-<browser>-linux.png`. Linux is the
  current merge gate. Existing Darwin files are historical/non-gating and are
  not regenerated by the supported workflow.
- Update selected scenes: `VRT_LINUX_UPDATE=1 bash scripts/vrt-linux.sh <spec...>`,
  followed by the cleanup and image review below.
- Harness: `src/test-utils/vrt.tsx` (`renderForVRT`, `VRT_ROOT_TESTID`),
  `vrt.setup.ts` (global mocks), `vrt.clock.ts`, `vrt.viewports.ts`.
- Reference example: `src/test/vrt/feed/Home.vrt.test.tsx`.

## Writing a test

```tsx
const screen = await renderForVRT(<Component />, { viewport: VRT_VIEWPORT_DESKTOP });
await expect(screen.getByTestId(VRT_ROOT_TESTID)).toMatchScreenshot('name-desktop');
```

### Light mode captures

Scenes render the dark `:root` tokens by default. Pass `theme: 'light'` to
capture the `.light` token set instead: the harness writes the shared
`pubky-theme` preference and toggles `.light` on `<html>` exactly as `ThemeSync`
does at runtime, and resets both to dark on every render so a light scene never
leaks into the next one. Name light baselines with a `-light-` segment before
the viewport (for example `cart-single-seller-light-desktop`).

```tsx
const screen = await renderForVRT(<Component />, { viewport: VRT_VIEWPORT_DESKTOP, theme: 'light' });
await expect(screen.getByTestId(VRT_ROOT_TESTID)).toMatchScreenshot('name-light-desktop');
```

### Surface captures (`expectVrtSurface`)

When a scene should capture one production surface rather than the whole
viewport (a dialog, a form section, a cart group), the production component
marks its root with `data-surface="<name>"` and the test asserts through the
guard before capturing — the capture then wraps exactly that element
(including portaled dialog content, which sits outside the VRT root in the
DOM but inside its screenshot region):

```tsx
await expect(await expectVrtSurface('pickup-reveal-dialog')).toMatchScreenshot('orders-pickup-reveal-desktop');
```

A scene without the production `data-surface` root is rejected by the guard
(see the negative test in `src/test/vrt/marketplace/MarketplacePickup.vrt.test.tsx`),
so a test-only stand-in can never be baselined by accident.

`renderForVRT` wraps the tree in a viewport-clamped root (the screenshot is
the viewport when capturing `VRT_ROOT_TESTID`). Time is frozen by `vrt.setup.ts`
before app modules load; the renderer seeds `Math.random` and waits for fonts +
successfully loaded images. Mock every data dependency (store/hook/fetch/router) so the pixels are deterministic.

## Determinism

Renders should be as close to identical as possible every run, on every OS.
`vitest.config.ts` sets two screenshot tolerances. The `vrt` project
(`allowedMismatchedPixels: 80` and `allowedMismatchedPixelRatio: 0.00005`;
the matcher uses the more restrictive of the two) is small enough that a
one-word label change fails. A looser 0.1% ratio previously hid a marketplace
badge rewrite on desktop captures. The `vrt-marketplace` project uses
`allowedMismatchedPixelRatio: 0.02` and pixelmatch `threshold: 0.2` (no pixel
cap) so 0.01–0.02 run-to-run badge-disc AA and hover raster — the class that
halted shop-v0.6.10, shop-v0.6.11, and shop-v0.6.12 — does not fail the
release train, while a real layout rewrite still exceeds 2%. Both are shared
by comparison (`npm run test:vrt`) and regeneration (`--update`): `--update`
only rewrites a baseline when a capture differs by more than the allowance.
Prefer a per-scene `comparatorOptions` override over raising the
non-marketplace values. Feed and onboarding desktop shells that include dense
tab chrome use `VRT_DENSE_CHROME_SCREENSHOT` from `src/test-utils/vrt.tsx`
(cap 1600 px / 0.3%) because Inter Tight AA and leftover `:hover` on those
glyphs is hundreds of pixels on 1440×900 — still well below rewriting a
marketplace badge under the global 80 px cap.
Pin every deterministic source below so real diffs stand out:

- **Async data** — mock the hook/controller to a fixed value. An unmocked fetch
  resolves differently per run/region. This is the #1 cause of flakiness.
- **Time** — `vrt.setup.ts` freezes time before app modules load and pins
  formatting to UTC. Use the stable clock in `vrt.clock.ts` for time-dependent
  fixtures; do not add real-time values to a scene.
- **Randomness** — `Math.random` is seeded by the harness, so name generators
  and placeholders stay stable.
- **Images** — `next/image` is mocked to a plain `<img>` in `vrt.setup.ts` (the
  browser runtime has no Next image optimizer, so the real component 404s).
  `renderForVRT` waits until each `<img>` has real pixels (`naturalWidth > 0`),
  then `decode()`, then two animation frames so SVG/logo paint cannot race the
  screenshot. Each image has a short timeout that rejects with the URL (and
  `complete` / `naturalWidth`) so a hung load is not mistaken for a generic
  test timeout. Load/decode failures reject with the image URL — broken assets
  must not become blank baselines. Swallowing `decode()` alone was not enough
  and caused intermittent blank header logos. Intentionally absent artwork
  should be mocked out of the tree rather than left as a broken `<img>`.
  **CSS `background-image` is not covered by that wait** — covers and other
  decorative backgrounds settle only via `toMatchScreenshot` retries unless
  you preload them first. Always `preloadImages(...)` (exported from
  `src/test-utils/vrt.tsx`; decodes via `new Image()`) for any CSS background
  URLs the surface paints, the same way Collections VRT does for card/hero
  covers before `renderForVRT`. Static `<img>` assets (e.g. logo SVGs) are
  covered by the wait, but a cold fetch can still race the initial paint —
  `preloadImages(...)` them too when a surface has flaked on a specific asset.
- **Hover transforms** — marketplace listing/drop cards use
  `transition-transform duration-300` plus `hover:scale-105` and a random
  `--card-hover-rotation`. They also run `.marketplace-card-enter`
  (`420ms both`, delay `index * 60ms`). The `vrt-marketplace` project
  rewrites shared `transition: none` to `transition-duration: 0s` so the
  hover end-state paints on the first frame, and **leaves `animation: none`**
  so the delayed enter `from` keyframe (`translateY(18px) scale(0.96)`)
  cannot compose with hover. Zero-motion CSS sets `animation-name: none`
  and `animation-delay: 0s`; it must not replace `animation: none` with
  duration-only `animation-duration: 0s`. Files run serially
  (`fileParallelism: false`). Capture hover scenes with
  `hoverAndWaitForScale` from `src/test-utils/vrt.tsx`: finish leftover
  animations on the VRT root, re-assert `:hover`, then wait until
  `getBoundingClientRect().width` is ≥ the pre-hover rest width × 1.04
  and no CSS animations are running. Do not wait on `offsetWidth` (layout
  ignores transforms) or `getComputedStyle().transform` / `scale` (they
  report the target immediately).
  Never rewrite `animation: none` to `animation-duration: 0s`: hover is a
  transition, card-enter is an animation; duration-only re-enables delayed
  fill-mode `from` and composes with hover.
  Playwright `locator.hover()` also scrolls a bottom-row card into view
  inside overflow-hidden `VRT_ROOT` (~39px, ±8px vs the committed crop).
  Call `hover({ force: true })` as a method (do not extract it) and pin
  `VRT_ROOT` at scroll 0 before capture so the scene is rest layout plus
  hover, not a scrolled crop.

- **Avatars** — VRT profile fixtures use `image: null` so every avatar renders
  `FacehashAvatar`. `vrt.setup.ts` sets `globalThis.__VRT__` and stabiliser CSS;
  `FacehashAvatar` disables blink, 3D tilt, and hover when that flag is set.
- **vi.mock + import order** — factories are hoisted; keep the
  `eslint-disable simple-import-sort/imports` header so `eslint --fix` can't
  reorder imports into a TDZ crash. Don't reference a top-level `const` inside a
  `vi.mock` factory (it's hoisted above the const) — inline the literal.

## Render like the real app

A template alone misses chrome the root layout adds. Onboarding pages render
under `<Header />` (the step bar), mounted by `src/app/layout.tsx`. Render that
wrapper in the test and mock what it reads (`usePathname`, `useAuthStore`,
`usePublicRoute`) so the snapshot matches what the user sees.

## Viewport crops and tall surfaces

Capturing `VRT_ROOT_TESTID` gives a viewport-sized crop. Content below that root's
fold is outside the baseline. For a complete production surface, use
`await expectVrtSurface(name)`: it finds the production `data-surface` root,
expands both the browser and Vitest iframe when needed, and resets scrolling
before returning an element locator. The screenshot covers that element's border
box, including portaled surfaces. See `prepareVrtSurfaceCapture` in
`src/test-utils/vrt.tsx`.

Choose the capture region intentionally and keep it stable. Do not replace a
full surface with a viewport crop, or switch to a full-page document screenshot,
to make a failing baseline pass. A baseline change must represent an intended
product change.

## Artifact: sub-pixel seams on segmented elements

A baseline may show thin tick lines that you don't see in your real browser.
Example: the onboarding progress bar (`molecules/ProgressSteps`) is 5 adjacent
`<div>` segments (`gap-0`), each with its own fill; the seams between them show
as faint notches.

Adjacent pieces can show sub-pixel rasterization seams at the test's device-pixel
ratio. Compare with the production surface and repeat the pinned Linux capture
before treating a seam as a rendering artifact. Accept only an understood,
repeatable result; an unexplained new seam is still a visual change to investigate.

## Running the Linux gate

Install the dependencies for the checked-out revision and start Docker. The
runner installs Linux dependencies into a separate Docker volume, uses the
pinned Playwright image and serializes projects/browsers. No arguments runs both
`vrt-marketplace` and `vrt`, in Chromium and Firefox:

```bash
npm run test:vrt
bash scripts/vrt-linux.sh src/test/vrt/marketplace/MarketplacePickup.vrt.test.tsx
```

Use full spec paths for targeted work. Do not invoke both Vitest projects in one
process: their browser instance names overlap. Keep `package-lock.json`, the
installed Playwright version and the pinned image in sync; see the checks in
[`ecommerce/release.md`](ecommerce/release.md#visual-regression-baselines).

The default pre-push gate runs related unit tests, lint and typecheck; it does
not run VRT. `PREPUSH_FULL=1 bash scripts/prepush.sh` adds related Linux VRT.
A shared harness/mock change requires the full VRT suite, not only related specs.

## Updating baselines

Regenerate only scenes intentionally changed by the PR, after the last UI change,
and keep the baseline changes in a PNG-only commit. Start with a clean screenshot
working tree: the cleanup helper restores or removes changed PNGs outside the
named spec directories, so do not mix unrelated image work into this operation.

```bash
VRT_LINUX_UPDATE=1 bash scripts/vrt-linux.sh src/test/vrt/marketplace/MarketplacePickup.vrt.test.tsx
bash scripts/vrt-revert-outside.sh src/test/vrt/marketplace/MarketplacePickup.vrt.test.tsx
git status --short -- '**/__screenshots__/**'
```

The update flag can rewrite multiple scenes in the selected files. Inspect every
changed path and keep only the intended Linux baselines. Open at least two new
images (or all of them if fewer), confirm they show the intended state, and check
that distinct scenes did not become duplicate or blank captures. Never re-pin an
untouched scene or raise tolerance to hide a product/layout mismatch. Report an
unrelated failure to the train owner with the scene name and diff ratio.

Prove a hypothesis on one scene before regenerating many. If a shared helper
(`vrt.tsx` / `vrt.setup.ts`) changes, inspect one resulting image first and then
run the full suite. Local regeneration in the pinned Linux container is supported;
native macOS captures are not the merge baseline.

## CI comparison and baseline update

`.github/workflows/vrt-marketplace.yml` supplies `vrt-marketplace` and `vrt-core`
for PRs targeting `master` or `release/shop-*`, and for `merge_group`. On PRs,
path filters skip unrelated changes while still reporting the jobs; filter errors
fail closed. Merge groups run both VRT jobs. A feature PR to a `train/shop-*`
branch does not trigger this workflow; the train-to-master PR supplies these
checks before the release merge. Do not treat a missing VRT job on a train PR as
a successful visual test.

The separate `.github/workflows/vrt.yml` runs Linux VRT on supported push events
and manual dispatch; it is not the PR merge gate. The live
[master ruleset](https://github.com/pubky/pubky-marketplace/rules/26693412)
defines which job results are required to merge.

CI regeneration currently commits baselines only under `src/test/vrt/`:
`.github/workflows/vrt-update-baselines.yml` limits its staging step to that
folder. For colocated specs elsewhere, such as
`src/components/molecules/Toaster/Toaster.vrt.test.tsx`, use the pinned local
Linux regeneration procedure above and commit the reviewed PNGs. Passing such a
spec to the CI workflow can regenerate images without committing them.

For specs under `src/test/vrt/`, open Actions → **VRT Update Baselines**, select
the PR branch and supply explicit space-separated spec paths in the required
`files` input. The workflow:

- Runs Chromium and Firefox in the pinned Linux Playwright container.
- Updates the named specs and cleans up PNGs outside that set.
- Commits and pushes changed Linux baselines to the selected branch; it does not
  open a separate PR or create a special `dev` branch.
- Skips the regeneration job on `master` and `main`.
- Makes no commit when the staged baseline diff is empty.

Review the resulting images and diff before accepting either local or CI
regeneration. The workflow is not permission to accept an unexplained visual
change.

## Missing marketplace baselines

A missing Linux baseline fails the PR comparison, just like a mismatch. The
marketplace CI script records missing images into the
`vrt-marketplace-linux-baselines` artifact to help diagnose/recover the missing
files; the failed comparison is not converted into a pass. Add reviewed baselines
from the pinned Linux regeneration process or that artifact and rerun comparison.

Fonts come from the vendored `@fontsource-variable/inter-tight` and
`@fontsource-variable/jetbrains-mono` packages in `vrt.setup.ts`. Do not substitute
a system font or rename a Darwin PNG to `*-linux.png` to silence a mismatch.

## Three consecutive runs before a flaky-gate PR

A VRT gate that failed once is not dismissed as a flake after one successful
retry. For a change intended to fix a flaky gate, run the same full Linux command
three times against the same HEAD and matching Playwright version:

```bash
npm run test:vrt
npm run test:vrt
npm run test:vrt
```

A path-filtered rerun or a regeneration run does not count. If a run fails, fix
the scene or harness and establish the three consecutive passes again; do not
widen tolerances or regenerate untouched baselines to make the gate green. This
extra proof is for flaky-gate changes, not a requirement to repeat every ordinary
PR's already-passing checks.
